# EsnaftaVar Ecosystem Contrarian Review

**State:** RECOMMENDED — NOT OWNER APPROVED

## Challenge

The foundation branches are deliberately broad. Breadth is useful for preserving
future seams, but it is not evidence that every designed system belongs in the
first Esenler commercial pilot. The strongest counter-proposal is to ship the
smallest trustworthy local-discovery and verified-purchase loop, learn from real
operations, and keep expensive systems inactive behind documented boundaries.

## Findings

| System | Contrarian finding | Pilot recommendation | Revisit trigger |
|---|---|---|---|
| Customer App | Existing core is more valuable than replacing it with future abstractions | Preserve and close remaining physical/release gates | repeated real-customer failure |
| Merchant App | The 16-capability foundation is a destination, not the minimum launch tool | controlled verifier/listing path first | enough merchants to justify dedicated workflow |
| Universal variants | Premature across all 24 L1 domains | enable only where product identity is otherwise wrong | catalog collision/choice evidence |
| Full organization hierarchy | Enterprise-heavy for one-shop pilot merchants | keep an additive one-shop organization seam | first real multi-branch operator |
| Ads | Adds billing, policy, ranking and dispute risk before organic value is proven | no paid ads in pilot | stable organic demand and owner economics decision |
| Rewards | Creates funding, liability, fraud and support obligations | defer | authoritative amount/quantity and funding decision |
| Gamification | Levels/challenges/streaks risk cheapening local commerce and incentivizing spend | defer; factual badges only as future candidate | evidence of real customer value |
| Reputation | Sparse data makes composite scores unfair and opaque | show independent ratings/counts; no advanced score | statistically meaningful verified history |
| Operations | Enterprise case tooling is excessive, but no operations is unsafe | lean named operators, evidence log and manual runbooks | case volume or SLA pressure |
| Analytics | Perfect warehouse/outbox coverage is unnecessary; zero visibility is unsafe | small authoritative registry and release health | proven decision questions |
| QA/CI | Massive matrices can delay learning; unrecorded skips destroy trust | exact risk-based gates with honest BLOCKED/SKIPPED states | platform or backend expansion |

## Conclusions that changed earlier emphasis

- Merchant App foundation remains valid, but a full separate app is no longer a
  prerequisite for the first pilot if a secure controlled verifier path exists.
- Reward Engine is not a pilot differentiator until purchase value and funding are
  authoritative; the responsible default is no economic promise.
- Merchant reputation should begin as transparent source signals, not a proprietary
  score or purchasable badge.
- Event outbox, advanced realtime, universal variants and automated case workflows
  remain architectural options, not default implementation commitments.

## Non-negotiable minimum despite simplification

Simplification must not remove server authorization, exact-shop QR binding,
single-winner consumption, immutable verified evidence, review uniqueness,
role-escalation protection, client-safe secret boundaries, rollback evidence or
physical release acceptance. Removing those is risk transfer, not simplification.
