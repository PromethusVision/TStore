# Merchant App Owner Option Simulation

Status: **HYPOTHETICAL — NO OWNER SELECTION**
Wave: 17 / WP93

| Root | Conservative option result | Recommended option result | Expansive option result |
|---|---|---|---|
| RD-01 | Manual review slows onboarding | Allowlist speeds ordinary shops, risks remain closed | Self-serve all creates policy exposure |
| RD-02 | One-shop model fast but future rewrite | Org foundation with simple UX supports growth | Enterprise hierarchy delays pilot |
| RD-03 | Owner-only lowers support, weak cashier fit | Narrow presets balance operations/security | Custom roles increase misconfiguration |
| RD-04 | Product+listing loses material variant truth | Three layers preserve evidence/listing truth | Merchant global identity corrupts catalog |
| RD-05 | Approval-before-draft loses merchant work | Private draft + governed approval preserves both | Immediate publication increases duplicates/abuse |
| RD-06 | Strict short TTL causes regeneration | Confirm-time atomic consume is secure/simple | Reservation/offline expands race/fraud complexity |
| RD-07 | Single quantity source can misstate purchase | Requested + actual snapshot is honest | Free-form units make comparison unreliable |
| RD-08 | Retail-only excludes service presence | Service shop presence without booking limits scope | Full booking becomes a new product |
| RD-09 | Minimal metrics reduce value | Aggregate views/directions under privacy gives insight | Customer-level analytics violates trust |
| RD-10 | Read/report only limits dialogue | Same as pilot recommendation | Replies add moderation/retaliation risk |
| RD-11 | Label-only lets stale stock persist | Reminder→unknown balances truth/effort | Auto out-of-stock may hide valid offers |
| RD-12 | No bulk increases repetitive work | Availability-only bulk limits blast radius | Bulk price/retire creates incidents |
| RD-13 | Canonical-only lacks local evidence | Moderated local media adds realism | Direct canonical promotion damages shared facts |
| RD-14 | In-app only may miss critical actions | Critical push + inbox balances reach/privacy | Broad channel use overloads merchants |
| RD-15 | Web-first reduces mobile release work | Separate Flutter fits QR and security | Single customer/merchant app couples risks |
| RD-16 | Restricted audit is safe but opaque | Recent history supports correction | Long export adds privacy/semantics burden |
| RD-17 | Four tabs simplify | Test frequency before choice | Five+ destinations can overwhelm |
| RD-18 | No visible placeholder prevents promises | Contract hooks preserve future path | Coming-soon UI creates unsupported expectations |

## First simulation conclusion

The recommended set produces the smallest commercially useful pilot while preserving organization growth, catalog integrity and QR trust. This is an architecture hypothesis, not approval.
