# EsnaftaVar Taxonomy Stable ID Migration Strategy

**State:** DESIGN ONLY — NO IDS GENERATED, NO SCHEMA OR RUNTIME CHANGE

## 1. Objective

The legacy 651-node taxonomy has no opaque immutable node identifier. Its `slug`
is the only exact machine locator, parent links are slug-based, and paths are
derived from mutable Turkish labels/slugs. The future canonical taxonomy needs an
identity model that survives rename, slug change, and most semantic-preserving
moves without rewriting history.

This document defines that model conceptually. It does not choose a UUID format,
generate production IDs, create a database schema, or authorize migration.

## 2. Recommended canonical node identity

Every future canonical node should eventually carry:

| Field | Identity rule |
|---|---|
| Immutable opaque stable ID | Primary identity. Generated by approved migration tooling, never derived from name, slug, or path. |
| Turkish display name | Mutable presentation data. A rename does not normally change identity. |
| Slug | Mutable routing/discovery locator with uniqueness and redirect rules. |
| Parent stable ID | Mutable hierarchy relation; null only at L1. |
| Level | Derived/validated hierarchy depth, currently 1–4. |
| Lifecycle state | At minimum active/assignable, inactive/unassignable, and retired/historical. |
| Aliases | Typed historical redirects and search terms, stored separately from the canonical slug. |
| Predecessor/successor edges | Explicit graph for merge, split, and retirement history. |
| Taxonomy version metadata | Records when the node/relation became effective and the approving decision. |

Recommended invariant: a product assignment, historical event, review, analytics
record, or saved filter references the stable ID. Display paths and slugs are
resolved at read time for the appropriate taxonomy version.

## 3. Values that must not define immutable identity

Do not derive or deterministically recompute the stable ID from:

- Turkish display name;
- slug;
- parent path or display path;
- sort order;
- localized merchant/customer label;
- a concatenation or hash of any of the above.

All of these can legitimately change. Deriving identity from them would turn a
rename or move into an apparent delete-and-create operation and would fragment
analytics, links, reviews, and assignments.

The legacy slug may be stored as a source locator during migration, but it does
not become the new immutable ID merely because it is unique in the source file.

## 4. Transition identity record

Before any runtime migration, an approved mapping dataset should bind:

1. source taxonomy version and source hash;
2. exact legacy locator (`slug` in the current source);
3. assigned canonical stable ID, if the mapping is one-to-one;
4. action and target-state evidence;
5. predecessor/successor edges for non-one-to-one cases;
6. approval decision and effective version;
7. manual or deterministic product reassignment rule where required.

The mapping must be immutable once used in a deployed migration. Corrections
should create a new versioned decision rather than rewriting historical evidence.

## 5. Rename rule

**Default: keep the stable ID.**

A label or slug rename that preserves semantic identity updates mutable fields,
not identity. The previous slug becomes a typed `LEGACY_REDIRECT`; historically
useful names may also become search synonyms, but only after independent quality
review.

Required checks before preserving the ID:

- inclusion/exclusion meaning is unchanged;
- product population does not need reclassification;
- no formerly separate concepts were added or removed;
- risk/policy scope is unchanged or explicitly versioned.

## 6. Move rule

**Default: keep the stable ID when the product concept is unchanged.**

A move changes `parent_stable_id` and the derived path. Stable identity can remain
when the same products still belong to the node and only the cross-domain or
navigation boundary changed. The old slug/path becomes a legacy redirect to the
same ID. Saved paths should be re-resolved, not treated as identity.

A move is not identity-preserving when the target redefines the product set,
combines a rename with material scope change, or introduces a policy boundary.
Such cases require a new successor or manual review.

Examples likely to preserve identity after validation include SSD moving from the
legacy Computer Components umbrella to final `Veri Depolama`. Vehicle-primary
phone holders are not a simple move because the legacy node also contains
desk/phone-primary holders; that case is a split.

## 7. Merge rule

A merge is represented as **multiple predecessor IDs to one successor ID**.

Recommended default when the successor has a broader or newly defined semantic
scope: create a new canonical stable ID, retire predecessor nodes from new
assignment, and link every predecessor to the successor. A dominant predecessor
ID may be retained only if an explicit owner decision proves that the successor is
the same concept and the other predecessors are true duplicates—not merely
siblings sharing a future container.

Old IDs and slugs remain resolvable for history and redirects. Historical facts
continue to point to their original IDs; reporting may roll them up through the
successor graph. Product reassignment to the successor requires validation of
policy and facet compatibility.

The current audit asserts zero exact merges. This is fail-closed: multiple legacy
leaves landing in one proposed L2 are not automatically semantic merges because
future L3/L4 leaves may preserve them.

## 8. Split rule

A split is represented as **one retired predecessor ID to multiple successor
IDs**. The predecessor must never silently redirect to one arbitrary child.

Each successor receives its own stable ID. The predecessor remains addressable
for history but becomes unassignable. Runtime resolution of the old ID must:

- apply a deterministic classification rule using reliable product attributes;
- otherwise return a disambiguation/manual-review state;
- never guess from a mutable display name alone.

Product assignments require reclassification. Historical analytics may continue
to group by the predecessor or be recomputed through explicit successor edges,
but the method must be versioned and disclosed.

Examples in the current final-domain bridge:

- `Oyuncak, Hobi & Müzik` → `Oyuncak & Hobi` plus `Müzik & Enstrüman`;
- `Araç & Masa Telefon Tutucu` → use-case-specific phone and automotive targets;
- `Bilgisayar Soğutma` → four final cooling leaves;
- coarse legacy Electronics/Computer L2 umbrellas → several final L2s.

## 9. Retire rule

A retired node keeps its stable ID and historical relations but becomes
unassignable. It must not be physically deleted merely because it no longer
appears in customer navigation.

Retirement records should include reason, effective version, replacement edges if
any, and whether legacy redirects remain valid. The current
`inactive_review` node `hediyelik-obje` is a retirement candidate; this audit does
not activate, delete, or select a successor for it.

## 10. Alias and redirect rule

Aliases are separate records, not alternate primary IDs. At minimum distinguish:

- `LEGACY_REDIRECT`: old slug/path resolves to a canonical stable ID or an
  explicit split-disambiguation response;
- `DISPLAY_ALIAS`: prior official label retained for compatibility;
- `SEARCH_SYNONYM`: customer query expansion that does not imply URL/ID identity;
- `MERCHANT_TERM`: seller-facing terminology, optionally scoped by domain;
- `TYPO_VARIANT`: normalization/alternate spelling with controlled precedence.

Each alias should record locale, type, source, target stable ID or split record,
lifecycle, effective version, and collision status. A search synonym must never be
used as evidence that two nodes are the same identity.

## 11. Collision and integrity controls

Future tooling should fail closed when:

- one active canonical slug resolves to multiple stable IDs in the same locale;
- a legacy redirect collides with another active canonical slug;
- a split predecessor is configured as a one-child redirect;
- parent links create cycles or depth exceeds four;
- a retired node is assigned to a new product;
- a mapping references an unapproved proposal as if it were final;
- a policy-gated node becomes sellable solely because taxonomy placement exists;
- the source hash differs from the audited source without a new reconciliation
  version.

## 12. Versioning and rollout sequence

Recommended design sequence, still requiring explicit future authorization:

1. owner-finalize the 22 L2 proposals;
2. complete owner-final L3/L4 designs where required;
3. freeze the stable-ID format and lifecycle/edge contracts;
4. assign IDs in deterministic migration input, not from names or paths;
5. finalize split/merge graph and policy dispositions;
6. dry-run against a Development copy with count and referential checks;
7. validate product reassignment and alias/redirect behavior;
8. adapt runtime reads/writes and analytics to stable IDs;
9. authorize Production migration separately.

## 13. Strategy result

- Rename: preserve stable ID when semantic identity is unchanged; retain old
  slug/name as typed legacy alias.
- Move: preserve stable ID when only parent/path changes; re-evaluate when scope
  or policy meaning changes.
- Merge: explicit many-to-one predecessor graph; normally a new successor ID.
- Split: explicit one-to-many graph; new child IDs; predecessor retired and never
  arbitrarily redirected.
- Retire: preserve historical addressability, disable new assignment.
- Alias: typed, versioned, collision-checked, and separate from search synonyms.

outside this audit and was not performed.
